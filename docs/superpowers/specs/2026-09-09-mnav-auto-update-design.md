# mNAV電卓 前提条件の自動取得 — 設計

日付: 2026-09-09
対象: `index.html`(Metaplanet mNAV 電卓)

## 背景

前提条件(発行済株式数・BTC保有量・有利子負債・優先株残高)をハードコードしていたため、
開示が更新されても手で直すまで古い数字が出続けていた。2026-09-09 時点で発行済株式数が
4.8% 古く、有利子負債が ¥20億 古く、本家 analytics.metaplanet.jp の EV mNAV 0.82 に対し
0.79 を表示していた。黙って古い値を出すのが最大の問題で、乖離に気付く手段が画面上に無かった。

## 調査結果: データ源

本家 analytics.metaplanet.jp は `data.strategytracker.com`(Google Cloud Storage の静的バケット)
から素の JSON を読んでいるだけで、**`Access-Control-Allow-Origin: *`** が付いている。
認証もレート制限も無く、GitHub Pages の静的ページから直接取得できる。

| エンドポイント | gzip後 | Cache-Control | 用途 |
|---|---|---|---|
| `latest.json` | 283 B | `max-age=60` | 現在の版数。約15分ごとに更新 |
| `prices-live.json` | 2.4 KB | `max-age=5` | 3350.T の株価 |
| `3350_T.v{版数}.json` | 808 KB | `max-age=31536000, immutable` | 前提条件一式 |

`3350_T.json`(版数なし)は 403。必ず `latest.json` で版数を得てから組み立てる。

### 使用するフィールドと単位

`3350_T.v{版数}.json` → `companies["3350.T"].processedMetrics` 直下:

| フィールド | 単位 | 2026-09-09 の実測値 |
|---|---|---|
| `latestTotalShares` | 株 | 1,345,340,624 |
| `latestDilutedShares` | 株 | 1,631,382,824 |
| `latestBtcBalance` | BTC | 43,000 |
| `latestDebt` | **USD** | 464,065,700 |
| `preferredStocks[].notionalMillions` | **円・百万** | 23,610 |
| `latestTreasuryDate` | 日付 | 2026-08-31 |
| `currencyInfo.fxRate` | **円→ドル** | 0.00651759 |

数値は 2026-09-09 に実測したスナップショット。為替は日々動くので、以下の検算の
細かい桁は再現しない。

`prices-live.json` → `prices["3350.T"]`:

| フィールド | 単位 | 実測値 |
|---|---|---|
| `price` | 円 | 246 |
| `currency` | — | `"JPY"` |

### 換算規則

**このファイルには向きの違う為替レートが2つ入っている。** 取り違えると桁が2万倍狂う。

```
currencyInfo.fxRate        = 0.00651759   円 → ドル
preferredStocks[].fxRate   = 153.431      ドル → 円   (= 1 / currencyInfo.fxRate、実測で完全に一致)
```

正準は `currencyInfo.fxRate` とし、そこから一度だけ反転して使う。
`preferredStocks[].fxRate` は参照しない(優先株が無い期は存在しないため)。

```
jpyPerUsd = 1 / currencyInfo.fxRate
debtJpy   = latestDebt × jpyPerUsd
```

優先株は配列なので**全要素を合算**する。要素ごとに通貨を見て換算する。

```
preferredJpy = Σ ( currency === "JPY"
                     ? notionalMillions × 1e6
                     : notionalUSD × jpyPerUsd )
```

現時点の要素は `MERCURY`(Class B Perpetual Convertible Preferred Shares)1件のみだが、
将来増えても合算されるようにしておく。

BTC価格は既存の CoinGecko →(失敗時)Kraken×為替 をそのまま使う。strategytracker には
円建て BTC 価格が無く、また現行の二重化は意図して作られた強みなので捨てない。

### 検算

上記の値と株価 ¥246、BTC価格 ¥12,079,068 で:

```
jpyPerUsd = 1 / 0.00651759                  = 153.431
BTC NAV   = 12,079,068 × 43,000             = ¥5,194.0億
有利子負債 = 464,065,700 × 153.431           = ¥712.0億
優先株    = 23,610 × 1,000,000               = ¥236.1億
時価総額   = 246 × 1,345,340,624             = ¥3,309.5億
EV        = 3,309.5 + 712.0 + 236.1          = ¥4,257.6億
EV mNAV   = 4,257.6 / 5,194.0                = 0.8197 → 0.81
mNAV      = 3,309.5 / 5,194.0                = 0.6372 → 0.63
```

スナップショット株価 ¥247 で計算すると EV mNAV は 0.8213 → **0.82** となり本家と一致する。

## 決定事項

| 論点 | 決定 |
|---|---|
| 自動化の範囲 | 前提条件4項目 + 3350の株価。BTC価格は現行のまま |
| 前提条件の取得頻度 | 1日1回 + 手動更新ボタン |
| 希薄化後の倍率 | 表示する(副次的な1行として) |
| 取得方式 | クライアントから直接。ビルド・Actions・プロキシは使わない |
| テスト | `index.html` からマーカー間を切り出して `node --test` |

### 取得方式にクライアント直叩きを選んだ理由

GitHub Actions で事前取得しリポジトリに小さな JSON を置く案(本家APIの変化を CI が検知できる、
クライアントが808KBを引かずに済む)も検討したが、以下の理由で採らない。

- このリポジトリの定義的な性質が「単一ファイル・ビルド不要・依存パッケージなし」で、README にもそう書いてある
- `index.html` をローカルでダブルクリックしても動く、という現在の使い勝手が壊れる
- 変化の検知は、取得値の妥当性チェックで実用上足りる

本家APIが実際に一度壊れたら、そのとき Actions 方式に切り替える。

## アーキテクチャ

### データ取得層

```
起動
 ├─ キャッシュ(無ければハードコード値)で即座に描画   ← 白画面を作らない
 ├─ prices-live.json           → 株価         [60秒ごと]
 ├─ CoinGecko / Kraken         → BTC価格      [60秒ごと・現行のまま]
 └─ 前回取得から24時間経過 or 手動更新ボタン
      └─ latest.json → 3350_T.v{版数}.json → 前提条件4項目
           └─ 検証を通れば localStorage に保存して描画を差し替え
```

既存の `SOURCES` 配列と `fetchJson` / `FETCH_TIMEOUT_MS`(12秒)をそのまま使う。

### localStorage

このツールは現在 localStorage を使っておらず、リロードのたびにハードコード値に戻る。
今回、**抽出後の数値のみ**を保存する(808KB の生JSONは保存しない)。

```json
{
  "shares": 1345340624,
  "dilutedShares": 1631382824,
  "btcHoldings": 43000,
  "debt": 71265677381,
  "preferred": 23610000000,
  "treasuryDate": "2026-08-31",
  "fetchedAt": "2026-09-09T09:12:00.000Z",
  "version": "20260909T010351Z"
}
```

読み書きは try/catch で囲み、プライベートウィンドウ等で例外が出ても描画を止めない。

### 純粋関数の切り出し

パース・検証・単位換算を副作用のない関数に分け、マーカーで囲んでテストから切り出せるようにする。

```js
/* --- PURE:BEGIN --- */
function parseAssumptions(companyJson) { ... }   // → 検証済みオブジェクト or null
function parseStockPrice(pricesJson) { ... }     // → 円建て数値 or NaN
/* --- PURE:END --- */
```

## 画面

### 希薄化後の見せ方

4つを同格に並べず階層をつける。現行の2つの大きな数字は発行済ベースのまま据え置き、
その下に希薄化後を小さく1行添える。株数の古さが問題の発端だった以上、
希薄化前後の**差そのもの**が常に見えている状態にしたい。

```
┌─────────────────────────┬─────────────────────────┐
│ EV mNAV倍率 (企業価値)  │ mNAV倍率 (時価総額)     │
│        0.81x            │        0.63x            │
│    ディスカウント -18.1% │   ディスカウント -36.3% │
├─────────────────────────┴─────────────────────────┤
│ 完全希薄化後   EV mNAV 0.95x  ・  mNAV 0.77x       │
│ 1,631,382,824株(ワラント等が全行使された場合)      │
└───────────────────────────────────────────────────┘
```

下の棒グラフ(EV / 時価総額 / BTC NAV)は発行済ベースのみで据え置き、増やさない。

### 手動上書き

現行の「BTC価格を手で編集すると自動更新が止まり『自動更新に戻す』で復帰」を、
自動化する全フィールドに広げる。新しい概念は持ち込まない。

- どれかを編集 → **そのフィールドだけ**手動に切り替わり、印と「自動に戻す」が出る
- 他のフィールドは自動のまま動き続ける
- 「もし250円だったら」の試算は今まで通りできる

現在の「既定値にリセット」は **「自動取得値に戻す」** に置き換える。
ハードコードの古い数字に戻すボタンは、自動取得がある以上むしろ有害なので削除する。

### 出所と鮮度

```
● 自動更新中 ・ CoinGecko ・ 10:06:00 取得              (現行)
● 株価 ¥246 ・ strategytracker ・ 10:06:00 取得          (新規)
● 前提条件 ・ 2026-08-31開示 ・ 本日 09:12 取得  [更新]  (新規)
```

3段目の状態表示:

| 状態 | 表示 |
|---|---|
| 取得成功 | `2026-08-31開示 ・ 本日 09:12 取得` |
| キャッシュ利用 | `2026-08-31開示 ・ キャッシュ(9/8 取得)` |
| ハードコードまで後退 | `自動取得できず ・ 2026-09-09時点の固定値`(赤系で強調) |

黙って古い数字を出すことが今回の乖離の原因だったので、最後の状態は目立たせる。
`[更新]` は前提条件の手動再取得。買い増しの開示があった日に押せば即反映される。

## エラー処理

### 単位の罠

間違えても数字が出てしまうため、検証で守る必要がある。

| 罠 | 誤ると | 対策 |
|---|---|---|
| `sharesOutstanding`(1,281,253,293)は**古い値**。`latestTotalShares` が正 | 今回のバグを再現する | フィールド名を定数化し、コメントで明示 |
| `latestDebt` は **USD** | ¥712億が¥4.6億になる | `jpyPerUsd` を掛ける |
| 為替レートが**逆向きで2つ**入っている | 掛けると2万倍、割ると2万分の1 | `jpyPerUsd = 1 / currencyInfo.fxRate` に一本化 |
| `preferredStocks[].notionalUSD` が隣にある | 桁が壊れる | `currency === "JPY"` なら `notionalMillions × 1e6` |
| `prices-live` に `priceUsd: 1.60` がある | mNAV が 0.004 になる | `currency === "JPY"` を確認してから `price` を使う |

### 検証項目

- 株数: 有限かつ正、`latestDilutedShares >= latestTotalShares`
- BTC保有量: 1,000 〜 1,000,000 BTC(既存の `MIN_PLAUSIBLE` の考え方に倣う)
- 為替: **反転後の** `jpyPerUsd` が 50 〜 300 の範囲外なら破棄(生の `fxRate` を直接見ない)
- `latestTreasuryDate` がキャッシュの日付より古ければ破棄(データの逆行を弾く)
- 株価: 正、かつ `currency === "JPY"`

### 全部か、ゼロか

一部だけの採用はしない。新しいBTC保有量と古い株数が混ざった状態は、
一貫して古いスナップショットより悪い数字を出す。4項目のうち1つでも検証に落ちたら
payload 全体を破棄し、キャッシュ → ハードコード値の順に後退する。

## テスト

`tests/run.mjs` が `index.html` を読み、`/* --- PURE:BEGIN --- */` から
`/* --- PURE:END --- */` までを `node:vm` で評価して純粋関数を取り出す。
Node 標準の `node --test` で実行し、依存パッケージは追加しない。配布物は今まで通り
`index.html` 1枚のまま。

`tests/fixtures/` に実際のレスポンスを記録して置く(company JSON は 3350.T の
`processedMetrics` のみに削って保存)。

### テストケース

1. 記録した company JSON から `debt = 71,265,677,381`(±1円)が出ること
2. 同じく `shares = 1,345,340,624` が出ること — **`sharesOutstanding` の 1,281,253,293 ではないこと**
3. `preferred = 23,610,000,000` が出ること(`notionalUSD` を拾っていないこと)
3b. 優先株を2要素(片方 USD 建て)にした fixture で、両方が合算され円建てになること
4. `prices-live` から `246` が出ること — `priceUsd` の 1.60 ではないこと
5. `currency` を `"USD"` に書き換えた fixture で `parseStockPrice` が NaN を返すこと
6. `latestDebt` を削った fixture で `parseAssumptions` が null を返すこと(部分採用しない)
7. `latestDilutedShares < latestTotalShares` の fixture で null を返すこと
8. `currencyInfo.fxRate` を 0.001(= jpyPerUsd 1000)にした fixture で null を返すこと
9. 為替を反転し忘れた実装を弾くための回帰: `debt` が ¥712億台であって
   ¥4.6億でも ¥1,400兆でもないこと

## 併せて直すもの

README の「残差 0.01 について」の節は**内容が誤っている**。本家の EV に出所不明の
約9億円が含まれると書いたが、実際は本家の EV mNAV タイルがスナップショット株価 ¥247 を、
株価・時価総額タイルがライブの ¥246 を使っているための表示タイミング差だった。
株価1円の差は時価総額13.5億に相当し、9億のズレを十分説明する。貸借対照表に
未知の項目があるわけではない。この節を書き直す。

## やらないこと

- BTC価格を strategytracker 系に寄せること(現行の二重化を維持)
- 過去の推移グラフ(company JSON には2,221日分の履歴があるが、このツールの目的外)
- 他のビットコイン保有企業への対応
- GitHub Actions による事前取得(本家APIが壊れたら再検討)

## リスク

`data.strategytracker.com` は公式に文書化された API ではなく、本家サイトの内部実装である。
フィールド名や構造が予告なく変わりうる。その場合の挙動は「検証に落ちてキャッシュ →
ハードコード値に後退し、画面に赤く『自動取得できず』と出る」であり、
黙って壊れた数字を出すことはない。これは現状(黙って古い数字を出す)より厳密に良い。
